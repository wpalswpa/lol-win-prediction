## 1. 목적·범위·표기

유스케이스 문서는 액터의 **목표 하나**를 한 장씩 적는다. 그래서 "소환사 복기가 끝난 뒤 코칭과 티어가 어떻게 이어지나", "재학습한 모델이 언제 사이트에 올라가나"처럼 **여러 UC 를 가로지르는 순서**는 UC 문서만으로는 보이지 않는다.
이 문서는 14개 UC 의 Sequence Diagram 에 적힌 메시지 순서와 기본흐름의 단계를 **시간 순 · 담당(레인) 기준**으로 다시 엮어 네 개의 비즈니스 프로세스로 묶고, 각 UC 를 결정·예외까지 포함한 액티비티 다이어그램으로 내렸다.

| 구분 | 무엇을 보이나 | 장수 | 원천 |
|---|---|:--:|---|
| 프로세스 조감 (L0) | 네 프로세스 P1~P4 가 서로 무엇을 넘겨주는가 | 1 | UC_00 §3·§5, §6 |
| 비즈니스 프로세스 (BP-1~4) | 프로세스마다 레인(담당)별 활동과 결정, UC 경계 | 4 | UC_01~UC_14 기본흐름·Sequence |
| 액티비티 (AD-1~14) | UC 하나의 활동 순서, 결정 분기(E·A 흐름 번호), 종료점 | 14 | 각 UC 문서 §5 |

**표기 약속**

- 레인 이름은 UC 문서의 lifeline 이름을 그대로 쓴다(이용자 · 화면·프런트 · 백엔드 · lolwin · Riot Games API 등).
- 결정 노드의 가지에 `(E3)` 처럼 붙은 번호는 그 UC 문서의 **예외흐름 번호**, `(A1)` 은 **대체흐름 번호**다. 다이어그램에서 UC 문서로 바로 찾아갈 수 있다.
- «include» · «extend» 는 UC 다이어그램의 관계를 그대로 옮긴 것이다. 액티비티에서는 포크(동시 호출) 또는 별도 활동으로 나타난다.
- 활동 안의 파일명·API 경로는 추적성을 위해 남겼다. 뜻은 각 UC 문서의 "쉽게 말하면"에 있다.

네 프로세스는 독립적이지 않다. P3 가 만든 모델을 P4 가 사이트에 올리고, P2 가 만든 표를 P1 이 읽고, P4 가 갱신한 열쇠가 P1 의 소환사 검색을 켠다.

| 프로세스 | 이름 | 포함 UC | 주체 | 주기 | 산출물 → 소비처 |
|:--:|---|---|---|---|---|

| P3 | 모델 변경·검증 | UC11 · UC12 | 팀원(분석·개발) | 피처·모델·문서를 바꿀 때마다 | `artifacts/model.joblib` · `schema.json` · `golden_predictions.json` → P4 |

#### 다이어그램 쉽게 읽기

1. **네 줄(레인)** 은 "누가 하는 일인가"다. 위에서 아래로 시간이 흐른다.
2. 팀원이 모델을 다시 공부시키고 검사해서 금고(GitHub)에 넣으면, 서비스 담당이 그것을 서버에 올리고 매일 열쇠를 갈아 끼운다.
3. 그 뒤 두 갈래가 **동시에** 돈다(굵은 가로선). 한쪽에서는 로봇이 밤에 자료를 모으고, 다른 쪽에서는 이용자가 사이트를 쓴다.
4. 맨 아래 "외부 시스템" 줄은 우리가 만들지 않은, 자료를 주는 곳이다. 어느 프로세스든 필요할 때 거기에 물어본다.

## 6. 표기 규칙과 표준 준수 노트

| 이 문서의 기호 | UML 2.5.1 Activity | BPMN 2.0 대응 | 뜻 |
|---|---|---|---|
| `\|레인\|` 세로 구획 | ActivityPartition (swimlane) | Pool / Lane | 누가 하는 일인가 |
| 검은 점 → / → 테두리 점 | InitialNode / ActivityFinalNode | Start Event / End Event | 시작·종료 |
| 마름모 + 가지 라벨 | DecisionNode / MergeNode | Exclusive Gateway (XOR) | 조건 분기. 가지 라벨의 `(E·A 번호)` 는 UC 문서의 흐름 번호 |
| 굵은 가로선 (fork / end fork) | ForkNode / JoinNode | Parallel Gateway (AND) | 동시에 일어나는 일 |
| repeat … repeat while | Loop (DecisionNode + 되돌아가는 ControlFlow) | Loop Activity | 반복 |
| 접힌 종이 (note) | Comment | Text Annotation | 대체흐름·주의 |
| «include» / «extend» 표기 | UseCase 관계를 활동 라벨로 옮김 | Call Activity | 다른 UC 의 흐름을 호출 |
| detach | 흐름 종료 없이 끊김 | — | 외부 시스템 레인은 흐름의 끝이 아님을 표시 |

- 액티비티 다이어그램의 활동 순서는 각 UC 문서의 **기본흐름 단계 순서**와 같고, 결정 가지는 **예외흐름·대체흐름**에서만 가져왔다. 원천에 없는 활동·분기는 만들지 않았다.
- BPMN 전용 요소(메시지 이벤트, 타이머 이벤트, 데이터 객체 기호)는 PlantUML Activity 로 직접 그릴 수 없어 활동 라벨과 §5 표로 대신했다. 타이머에 해당하는 것은 "24시간 만료"(UC14)·"5분 대기"(UC10 loop)·"5분 캐시"(UC3) 셋이다.
- 미확정 사항은 다이어그램 안에 `자료 없음 — 확인 필요` 또는 `[추론]` 으로 그대로 적었다(P2 실행 주기, DB 접속 실패 시 종료, CSV 즉시 반영).
